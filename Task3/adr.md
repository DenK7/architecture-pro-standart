### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Диаграммы

| Диаграмма | Файл draw.io |
|---|---|
| C4, уровень 1 — контекст | [c4-context-deposit-mvp.drawio](c4-context-deposit-mvp.drawio) |
| C4, уровень 2 — контейнеры (детализированы интернет-банк и АБС, а также интеграционная платформа, сайт и система КЦ) | [c4-container-deposit-mvp.drawio](c4-container-deposit-mvp.drawio) |

На диаграммах цветом отмечено: синий — новый элемент, бирюзовый — существующий элемент с доработками, серый — без изменений. Сплошная линия — синхронный вызов, оранжевый пунктир — обмен через Kafka. На связях указаны номера Use Cases.

#### Суть решения

1. **Новые функции депозитов — в отдельных сервисах рядом с монолитом интернет-банка (Strangler Fig).** Монолит только встраивает микрофронтенд, проверяет сессию и отдаёт список счетов. Так ядро подрядчика не трогаем, а новые сервисы можно развернуть в двух ЦОД и масштабировать горизонтально.
2. **Вся связь онлайн-каналов с АБС — асинхронная, через Kafka.** Заявки ждут в топике, пока АБС их не заберёт. Ставки и статусы приходят из АБС событиями. Каналы читают только свои копии данных, поэтому онлайн-нагрузка не попадает в БД АБС, а сбой АБС не останавливает приём заявок.
3. **АБС подключается к Kafka стандартными коннекторами Kafka Connect, без доработки PL/SQL под брокер.** JDBC Sink пишет заявки в таблицы АБС пакетами с ограничением скорости. Debezium читает изменения ставок и статусов из журналов Oracle (LogMiner) и публикует их в Kafka, не нагружая БД запросами.
4. **Ставки и согласование ставки переносятся из Excel и e-mail в АБС.** Там уже работают сотрудники бэк-офиса и есть ролевая модель для разграничения депозитов и кредитов.
5. **СМС-коды и уведомления — в собственных сервисах банка** (OTP-сервис и сервис уведомлений поверх существующего СМС-шлюза), без доработки ядра интернет-банка.

| Топик | Отправитель | Получатели | Содержимое | UC |
|---|---|---|---|---|

#### Логика выбора технологий

- **.NET 8 для новых сервисов.** Команда интернет-банка знает C#, а современный .NET работает с Kafka (Confluent.Kafka) и запускается на Linux. Монолит на .NET Framework 4.5 с Kafka несовместим, поэтому брокер подключается только к новым сервисам.
- **MS SQL для БД сервисов.** СУБД уже используется в интернет-банке, есть экспертиза и лицензии. Отказоустойчивость между ЦОД обеспечивает Always On Availability Groups.
- **Kafka.** Её прямо указали брокером «на перспективу». Она хранит события и позволяет перечитать их, например чтобы восстановить кэш ставок. Kafka Connect даёт готовую интеграцию с Oracle без переписывания АБС, а значит, позже на тот же механизм можно перевести суточные обмены кредитного направления.
- **YARP в API Gateway.** Это библиотека на .NET, поэтому собственный шлюз собирается и сопровождается командой интернет-банка без новой технологии.
- **Java, Spring Boot для модуля КЦ.** Это стек платформы КЦ и её механизм расширения. Java-специалисты есть в команде АБС.
- **Развёртывание.** Новые сервисы — в двух ЦОД, active-active за балансировщиком. Kafka и MS SQL реплицируются между ЦОД. Платформу контейнеризации выбирают при детальном проектировании. Для MVP достаточно виртуальных машин с CI/CD и rolling-обновлениями.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Доработать монолит интернет-банка и интегрироваться с АБС, как сейчас, через её БД или будущее API.** Отклонено: растёт нагрузка на перегруженную БД АБС, доступность интернет-банка зависит от АБС, монолит не масштабируется и не работает с Kafka, а доработки ядра зависят от подрядчика.
2. **Синхронный REST-фасад над АБС вместо Kafka.** Отклонено для онлайн-каналов: при каждом запросе клиента нагружается АБС, а её сбой сразу останавливает приём заявок. Это противоречит требованиям 99,9% и изоляции АБС.
3. **RabbitMQ вместо Kafka.** RabbitMQ совместим со старым стеком, но отклонён. Он не хранит события для повторного чтения, у него нет зрелых коннекторов к Oracle, хуже работа в двух ЦОД. К тому же это противоречит требованию использовать Kafka на перспективу.
4. **Своя публикация событий из АБС: таблица событий и процедура опроса на PL/SQL или Delphi.** Отклонено в пользу Debezium: опрос таблиц создаёт постоянную нагрузку на БД АБС и требует больше собственного кода от команды АБС.
5. **Отдельный микросервис ставок со своим интерфейсом для бэк-офиса вместо доработки АБС.** Отложено. Сотрудники работают в АБС, согласование ставки по заявке и ролевая модель тоже живут в АБС. Для MVP дешевле доработать АБС, а вынос ставок в отдельный сервис можно рассмотреть в целевой архитектуре.
6. **СМС-коды через ядро интернет-банка.** Отклонено: нужна доработка подрядчика, которой по условиям лучше избежать.
7. **Заявки с сайта прямо в систему КЦ по REST.** Отклонено: публичный сайт оказался бы напрямую связан с системой подрядчика, а при её недоступности заявки терялись бы. Через Kafka заявки дожидаются обработки.
8. **Оркестрация процесса открытия депозита в BPM (Camunda уже есть у банка).** Отложено до целевого состояния. В MVP шаги выполняет бэк-офис в АБС, а автоматическое открытие без бэк-офиса через год может потребовать оркестратор.

**Недостатки, ограничения, риски**

| Риск или ограничение | Последствие | Как снижаем |
|---|---|---|
| Kafka в двух ЦОД: для кворума контроллеров KRaft нужно нечётное число площадок | При отказе ЦОД кластер может потерять кворум | Растянутый кластер с контроллером-свидетелем на третьей площадке либо отдельные кластеры в каждом ЦОД с репликацией MirrorMaker 2 и процедурой переключения |
| Debezium для Oracle требует supplemental logging и доступа к LogMiner | Нужны согласование с DBA и командой АБС, небольшой рост объёма redo-логов | Включаем логирование только для новых таблиц ставок и статусов, проводим нагрузочное тестирование |
| Нагрузка на команду АБС (20 чел.): таблицы, процедуры, формы Delphi, роли | Команда АБС может стать узким местом по срокам | В MVP АБС только хранит данные и даёт формы, интеграцию берут на себя стандартные коннекторы. Объём работ согласуем заранее |
| Итоговая согласованность (eventual consistency): ставки в каналах обновляются с задержкой в секунды | Клиент может увидеть ставку, которая уже изменилась | Ставка фиксируется в заявке и окончательно подтверждается бэк-офисом в UC7. Клиенту показываем «ставка на дату подачи» |
| В MVP заявки обрабатываются вручную | Скорость открытия депозита зависит от загрузки бэк-офиса | SLA обработки онлайн-заявок, мониторинг очереди. Через год — автоматизация на тех же событиях |
| Монолит интернет-банка дорабатывается (встраивание, сессия, счета) | Возможны ограничения платформы подрядчика | Доработки только в части, которую банк меняет сам. При ограничениях — консультация подрядчика |
| Список счетов по-прежнему берётся из монолита, который читает БД АБС | Остаётся часть старой нагрузки на АБС | Это существующая функциональность, не новая нагрузка. В целевой архитектуре счета реплицируются через CDC |
| Новые технологии для команды: .NET 8, Kafka, Kafka Connect, Debezium | Риск ошибок эксплуатации на старте | Обучение, пилот на стенде, поддержка вендора или интегратора по Kafka, наблюдаемость с первого дня |
| Больше элементов, чем в монолите: шлюз, сервисы, брокер | Сложнее эксплуатация, нужны мониторинг и сквозная трассировка | Единые шаблоны сервисов, CI/CD, централизованные логи и трассировка (S6) |
| Новый клиент с сайта может не прийти в отделение | Затраты кол-центра без продажи | Аналитика конверсии лидов, напоминания по СМС в следующих итерациях |
| ПДн появляются в новых БД и в Kafka | Расширяется контур обработки ПДн по 152-ФЗ | Шифрование топиков и БД, маскирование в логах, сроки хранения, ролевой доступ |
