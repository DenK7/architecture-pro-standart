### <a name="_b7urdng99y53"></a>**Название задачи:** Заявка на кредит онлайн: сайт и интернет-банк
#### <a name="_3bfxc9a45514"></a>**Функциональные требования**

**Контекст.** В течение года после MVP клиент должен подавать заявку на кредит в интернет-банке и на сайте и получать решение в течение одного дня, если данных для решения достаточно. Сейчас заявку принимают только в отделении: менеджер вводит её в АБС, заявки раз в сутки уходят через БД в Кредитный конвейер, рассмотрение занимает около недели. Ускорить суточный обмен между АБС и конвейером нельзя.

Решение использует архитектуру MVP депозитов (задание 3): каналы, API Gateway, OTP-сервис, сервис уведомлений, Kafka и Kafka Connect. Номера UC указаны на связях диаграмм.

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Диаграммы

| Диаграмма | Файл draw.io |
|---|---|
| C4, уровень 1 — контекст | [c4-context-credit-online.drawio](c4-context-credit-online.drawio) |
| C4, уровень 3 — компоненты Кредитного конвейера и системы скоринга. Каналы и интеграции показаны контейнерами | [c4-component-credit-online.drawio](c4-component-credit-online.drawio) |

На диаграммах показано только то, что затрагивает кредитный процесс. Элементы MVP, которые используются без изменений (OTP-сервис, сервис уведомлений, СМС-шлюз), обозначены серым.

#### Суть решения

1. **Онлайн-заявки идут в конвейер через Kafka, а не через АБС.** Сервис кредитных заявок публикует заявку в `credit.applications`, Online Application Listener конвейера запускает по ней процесс в Camunda. Так обходится суточный обмен, который нельзя ускорить, и заявка доходит до сотрудника за минуты. Суточный обмен с АБС остаётся для заявок из отделения и для передачи одобренных кредитов на выдачу.
2. **Два новых процесса в конвейере** на BPMN и DMN, которые IT-отдел банка уже умеет дорабатывать:
   - «Предварительное решение» — автоматическое решение для нового клиента по данным БКИ;
   - «Быстрая заявка» — упрощённый повторный скоринг и задача сотруднику со сроком «в тот же день».
3. **Предодобренные предложения считаются ночью** отдельным экземпляром скоринга по реплике данных и публикуются в Kafka. Интернет-банк показывает их из витрины и не обращается к скорингу. Требование не нагружать скоринг в рабочие часы выполняется.
4. **Скоринг получает новые режимы в своём API:** «новый клиент» (только БКИ) и «упрощённый повторный». К ним добавляется лимит запросов от онлайн-каналов.
5. **Сквозная заявка между сайтом и отделением.** Заявки с сайта через Kafka Connect попадают в АБС, где их находит сотрудник отделения. Когда заявка приходит в конвейер суточным обменом, Application Matcher связывает её с уже запущенным процессом через корреляцию сообщений Camunda по онлайн-идентификатору.
6. **Статусы и СМС — по образцу MVP депозитов.** Конвейер публикует события о смене статуса, Сервис кредитных заявок обновляет статус для клиента и отправляет запросы на СМС в общий сервис уведомлений.

#### Логика выбора

- **Kafka вместо прямого REST «каналы → конвейер».** Kafka уже есть в MVP. Если конвейер или скоринг временно недоступны, заявка не теряется: клиент сразу получает ответ «заявка принята», а обработка продолжается после восстановления. Это требование R5. Статусы по той же шине получают каналы и уведомления.
- **Предварительное решение — автоматически по правилам DMN.** Сотрудник не может ответить новому клиенту за 60 секунд, а правила в DMN бизнес и IT меняют без переразработки процесса. Окончательное решение всё равно принимает сотрудник после идентификации.
- **Ночной предрасчёт на отдельном экземпляре по реплике.** Это прямо следует из запрета нагружать скоринг днём. Данные для расчёта скоринг уже получает раз в сутки, поэтому новой интеграции с АБС не нужно.
- **Связь заявки с сайта и из отделения через АБС и корреляцию в Camunda.** Сотрудник отделения продолжает работать в привычной АБС. Конвейер не создаёт дубль, а продолжает процесс, запущенный онлайн.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Подавать онлайн-заявки через АБС**, как заявки из отделения. Отклонено: суточный обмен АБС → конвейер ускорить нельзя, решение за один день недостижимо. К тому же растёт нагрузка на перегруженную АБС.
2. **Синхронный REST «Сервис кредитных заявок → Кредитный конвейер».** Проще, ответ сразу. Отклонено: доступность каналов начинает зависеть от конвейера и скоринга, при их сбое заявки теряются или клиент получает ошибку. Через Kafka заявка принимается всегда.
3. **Каналы вызывают скоринг напрямую для предварительного решения.** Быстрее на один шаг. Отклонено: скоринг получает неконтролируемую нагрузку из интернета, логика решения размазывается по каналам, а заявка не попадает в конвейер, где по ней дальше работает сотрудник.
4. **Считать предодобренные предложения онлайн при входе клиента в интернет-банк.** Всегда свежий результат. Отклонено: создаёт дневную нагрузку на скоринг, что прямо запрещено требованием +R9.
5. **Отдельный сервис предварительного решения вне конвейера** (например, на .NET в каналах). Отклонено: дублирует логику кредитного процесса, которая уже автоматизирована в Camunda, и усложняет передачу заявки сотруднику.
6. **Сотрудник отделения работает с заявками с сайта прямо в интерфейсе конвейера, а не в АБС.** Убирает зависимость от суточного обмена при продолжении заявки. Отложено: для 500 сотрудников отделений это новое рабочее место и обучение. Можно вернуться к этому варианту в следующей итерации, если суточная задержка окажется критичной.
7. **RabbitMQ вместо Kafka для заявок.** Отклонено по тем же причинам, что и в ADR задания 3: Kafka уже выбрана как брокер «на перспективу», уже используется в MVP и хранит события для повторного чтения.

| Ограничение или риск | Последствие | Как снижаем |
