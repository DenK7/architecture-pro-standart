# Задание 2. FURPS — депозитное и кредитное направления (MVP)

Обозначения в колонке «Комментарий»:
- **АЗТ** — архитектурно-значимое требование: влияет на структуру решения, выбор технологий или интеграций;
- **Доп.** — дополнительное требование, которого нет в исходных вводных; рядом указано обоснование;
- в скобках — источник: *Деп* (депозитный процесс), *Кред* (кредитный процесс), *Общ* (оба направления).

| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | **Функциональные (Functionality)** | |
| F1 | Сайт показывает каталог депозитов с актуальными ставками | **АЗТ** (Деп). Ставки должны браться из единого источника (см. F3) и отдаваться публичным API без обращения к АБС в момент запроса |
| F2 | Сайт принимает заявку на депозит от нового клиента (Ф. И. О. и телефон). Заявка попадает в систему кол-центра, менеджер КЦ звонит и может предложить особые условия, затем приглашает клиента в отделение для идентификации | **АЗТ** (Деп). Нужна новая интеграция «сайт → система КЦ». Платформа КЦ расширяемая (CRM, Java/Spring Boot), а в команде АБС есть Java-разработчики, поэтому доработку можно сделать без ядра подрядчика |
| F3 | Ставки по депозитам ведутся в информационной системе, а не в XLS: базовые ставки, ставки по продуктам и срокам, история изменений. Работать со ставками могут сотрудники бэк-офисов депозитов и кредитов | **АЗТ** (Деп). Предлагаемое место — АБС, рядом с процессом согласования. При изменении ставки АБС публикует событие в Kafka, каналы обновляют по нему свой кэш, а не читают БД АБС |
| F4 | Согласование ставки по заявке, включая специальные ставки, выполняется в АБС как процесс между бэк-офисом депозитов и кредитованием, а не по e-mail | **АЗТ** (Деп). Убирает ручную цепочку писем из Задания 1. Права доступа учитывают разграничение данных между депозитами и кредитами (см. +R10) |
| F5 | Интернет-банк показывает каталог депозитов с актуальными ставками и персонализированные ставки для конкретного клиента | **АЗТ** (Деп). Персональная ставка рассчитывается по правилам из F3 и данным клиента. Показ должен укладываться в требования P1–P2 |
| F6 | В интернет-банке клиент подаёт заявку на открытие депозита: выбирает продукт, указывает счёт списания и сумму. Операция подтверждается СМС-кодом (OTP) | **АЗТ** (Деп). СМС-функционал ядра интернет-банка дорабатывать не нужно: OTP реализует собственный сервис банка, который отправляет коды через существующий СМС-шлюз |
| F7 | В MVP заявку из интернет-банка обрабатывает менеджер бэк-офиса: он подтверждает условия депозита в АБС. Интернет-банк не обращается к API или БД АБС напрямую | **АЗТ** (Деп). Заявки передаются асинхронно через Kafka. АБС вычитывает их из топика в своём темпе, поэтому онлайн-нагрузка не бьёт по её БД |
| F8 | Клиент получает СМС после подтверждения размера ставки и после открытия депозита | **АЗТ** (Деп). АБС публикует события о смене статуса заявки в Kafka. Сервис уведомлений подписан на топик и отправляет СМС через СМС-шлюз |
| F9 | Сайт и интернет-банк показывают витрину кредитных предложений и актуальные условия. Источник условий — Кредитный конвейер | **АЗТ** (Кред). Условия копируются из конвейера в кэш или витрину каналов, чтобы публичный трафик не шёл в конвейер |
| F10 | Сайт принимает заявку на кредит (Ф. И. О. и телефон). Если клиент дополнительно вводит паспортные данные, он сразу получает предварительное решение: скоринг по общим данным БКИ. После подачи заявки клиенту приходит СМС с приглашением в отделение для идентификации и получения кредита | **АЗТ** (Кред). Нужен онлайн-сценарий скоринга для клиента, которого нет в АБС: заявка создаётся в Кредитном конвейере, а он вызывает скоринг с данными только из БКИ |
| F11 | Сотрудник отделения продолжает работу с заявкой, поданной на сайте: находит её по паспорту или телефону. Для полностью нового клиента он создаёт новую заявку | **АЗТ** (Кред). Нужны сквозной идентификатор заявки и поиск по нему в АБС и Кредитном конвейере, иначе появятся дубли заявок и повторные запросы в БКИ |
| F12 | В интернет-банке клиенту показывается предодобренное предложение (рассчитанная заранее сумма). Клиент указывает счёт зачисления и данные, подтверждает заявку СМС-кодом. При подаче выполняется повторный упрощённый скоринг | **АЗТ** (Кред). Предодобренные предложения хранятся в отдельной витрине вне скоринга, а интернет-банк читает их оттуда |
| F13 | Заявки по предодобренным предложениям попадают в Кредитный конвейер и обрабатываются в тот же рабочий день | **АЗТ** (Кред). Суточный обмен АБС → конвейер ускорить нельзя (+R8), поэтому нужен отдельный онлайн-канал «интернет-банк → интеграционный слой → Кредитный конвейер» (REST или Kafka, обработчики Camunda на Java) в обход АБС |
| F14 | Предодобренные предложения рассчитываются заранее, пакетно и без нагрузки на скоринг в рабочие часы | **АЗТ** (Кред). Расчёт идёт ночью или в отдельном экземпляре скоринга по копии данных (см. P7, +R9) |
| F15 | Клиент получает СМС при каждом изменении статуса заявки на кредит | **АЗТ** (Кред). Конвейер публикует события о смене статуса (Camunda, Java) → Kafka → сервис уведомлений → СМС-шлюз |
| F16 | Создаётся единый сервис уведомлений клиентов: шаблоны, отправка через СМС-шлюз, учёт доставки. Его используют оба направления | **Доп.**, **АЗТ** (Общ). Сейчас СМС отправляет АБС, а в интернет-банке СМС живут в ядре подрядчика. Общий сервис позволяет не нагружать АБС и не дорабатывать ядро интернет-банка, а позже добавить push и e-mail |
| F17 | Весь трафик между клиентом и сайтом или интернет-банком шифруется (HTTPS, TLS 1.2 и выше). Внутри контура трафик между сервисами тоже шифруется (TLS или mTLS) | **АЗТ** (Общ). Прямое требование заказчика: с сайта и из интернет-банка передаются ПДн и финансовые данные. Шифрование внутри контура добавлено как **Доп.** |
| F18 | Персональные данные (Ф. И. О., телефон, паспорт) защищаются: доступ по ролям, маскирование в логах, шифрование при хранении для паспортных данных, сроки хранения необработанных заявок с сайта | **Доп.** (Общ). Сайт впервые начинает собирать паспортные данные. Это влияет на выбор хранилища и на устройство логирования |
| F19 | Перед запросом в БКИ клиент даёт явное согласие на получение кредитного отчёта, согласие сохраняется | **Доп.** (Кред). Без согласия запрос в БКИ невозможен. Согласие нужно хранить и передавать вместе с заявкой |
| F20 | Публичные формы сайта защищены от ботов и злоупотреблений: ограничение частоты запросов, CAPTCHA или подтверждение телефона | **Доп.** (Общ). Каждая заявка с сайта стоит денег: звонок кол-центра или платный запрос в БКИ. Без защиты возможны спам и расходы |
| F21 | Ведётся журнал аудита ключевых действий: подача заявки, ввод OTP, изменение ставки, решение по заявке, кто и когда | **Доп.** (Общ). Нужен для разбора споров с клиентом, требований безопасности, а также для контроля разграничения доступа |
| F22 | Приём заявок идемпотентный: повторная отправка или повтор сообщения не создаёт дубль заявки | **Доп.** (Общ). При асинхронной передаче через Kafka возможна повторная доставка. Дубль заявки на депозит или кредит — финансовый риск |
| U | **Удобство использования (Usability)** | |
| U1 | Интерфейсы сайта и интернет-банка соответствуют корпоративной дизайн-системе: фирменные цвета и брендированные элементы | **АЗТ** (Общ). Новые экраны в микросервисном фронтенде должны выглядеть так же, как монолит интернет-банка, поэтому нужна общая библиотека UI-компонентов |
| U2 | Формы содержат минимум полей. На сайте — Ф. И. О. и телефон, паспорт по желанию для онлайн-решения по кредиту. В интернет-банке известные данные клиента подставляются автоматически, клиент указывает только счёт и сумму | (Общ). Прямое требование бизнеса о максимальном удобстве |
| U3 | Сайт и интернет-банк корректно работают в мобильных браузерах (адаптивная вёрстка) | **Доп.** (Общ). Целевая аудитория — молодые клиенты, они в основном пользуются смартфонами |
| U4 | Интерфейс удобен для людей старшего возраста: читаемые шрифты, достаточный контраст, простые формулировки (ориентир — WCAG 2.1 AA) | **Доп.** (Общ). Основные текущие клиенты банка старшего возраста, их нельзя потерять при цифровизации |
| U5 | Клиент видит статус своей заявки в интернет-банке. При ошибке выводится понятное сообщение. Ввод СМС-кода поддерживает повторную отправку с таймером | **Доп.** (Общ). Снижает число звонков в кол-центр о статусе заявки |
| U6 | Сотрудники работают с новыми заявками в привычных системах: бэк-офис — в АБС, кол-центр — в системе КЦ, кредитование — в Кредитном конвейере | (Общ). Новых рабочих мест не добавляем: так меньше затрат на обучение 900+ сотрудников |
| R | **Надёжность (Reliability)** | |
| R1 | Все клиентские сервисы (сайт, интернет-банк, сервисы заявок, ставок и уведомлений) работают 24/7 с доступностью не ниже 99,9% | **АЗТ** (Общ). 99,9% — это не больше ~43 минут простоя в месяц, около 8,8 часа в год. Требует резервирования всех компонентов цепочки |
| R2 | При отказе ЦОД сервисы интернет-банка и новые сервисы остаются доступны и выдерживают полную нагрузку. Работа идёт в двух ЦОД с автоматическим переключением, каждый ЦОД рассчитан на 100% нагрузки | **АЗТ** (Общ). Текущий монолит на одной группе серверов этого не обеспечивает, как и говорит команда интернет-банка. Поэтому новые функции выносятся в отдельные сервисы с развёртыванием в двух ЦОД |
| R3 | Перегрузка или недоступность АБС не блокирует приём заявок: заявка принимается и сохраняется, а в АБС попадает после восстановления | **АЗТ** (Общ). Асинхронная интеграция через Kafka: заявка лежит в топике, пока АБС её не вычитает. Изолирует перегруженную АБС от онлайн-нагрузки |
| R4 | Заявки и события доставляются гарантированно (at-least-once), без потерь при сбоях. Неуспешные сообщения уходят в отдельную очередь для разбора | **АЗТ** (Общ). Вместе с F22 обеспечивает отсутствие и потерь, и дублей |
| R5 | Если скоринг или БКИ недоступны, заявка с сайта всё равно принимается. Решение сообщается позже по СМС | **Доп.** (Кред). Внешний сервис БКИ не должен ломать сценарий подачи заявки |
| R6 | Для новых сервисов: RPO ≤ 1 минуты для заявок, RTO ≤ 15 минут | **Доп.** (Общ). Нужно, чтобы уложиться в 99,9%: одна авария с восстановлением дольше 43 минут нарушает SLA за месяц |
| P | **Производительность (Performance)** | |
| P1 | Отклик пользовательских операций сайта и интернет-банка — в пределах сотен миллисекунд (p95 ≤ 500 мс), без учёта времени доставки СМС | **АЗТ** (Общ). Бизнес ожидает отклик «в миллисекундах», поэтому измеримая цель. Достигается асинхронной обработкой заявок: клиенту сразу возвращается «заявка принята» |
| P2 | Справочные данные (ставки, продукты, условия кредитов, справочники для платежей) загружаются за ≤ 100 мс (p95) | **АЗТ** (Общ). Сейчас некоторые справочники в платежах грузятся больше секунды. Нужен кэш или витрина справочников в каналах вместо чтения из АБС в момент запроса |
| P3 | Онлайн-каналы не увеличивают нагрузку на БД АБС. Чтение идёт из кэша или витрины, запись — через Kafka, АБС вычитывает сообщения с ограничением скорости | **АЗТ** (Общ). БД АБС перегружена, а сама АБС масштабируется только вертикально (+R4) |
| P4 | Новые сервисы масштабируются горизонтально. Запросы распределяются между экземплярами, серверами и ЦОД через балансировщики | **АЗТ** (Общ). Прямое требование. Сервисы должны быть stateless, а состояние храниться в БД или Kafka |
| P5 | Заявки по предодобренным кредитным предложениям доходят до Кредитного конвейера за минуты и обрабатываются в тот же рабочий день | **АЗТ** (Кред). См. F13 |
| P6 | Предварительное решение по кредиту на сайте выдаётся онлайн за ≤ 60 секунд. Если не успели — решение приходит по СМС | **Доп.** (Кред). Время ответа БКИ не под контролем банка, поэтому нужен асинхронный запасной вариант |
| P7 | Онлайн-каналы нагружают систему скоринга ограниченно (лимиты запросов). Предрасчёт предодобренных предложений выполняется вне рабочих часов | **АЗТ** (Кред). Скоринг критичен для банка и загружен днём |
| P8 | СМС-код доставляется клиенту за ≤ 30 секунд, уведомление о смене статуса — за ≤ 5 минут | **Доп.** (Общ). Иначе подтверждение операций перестаёт быть удобным. Требует мониторинга SLA телеком-оператора |
| P9 | Пропускная способность рассчитывается с запасом не меньше ×10 к текущей нагрузке интернет-банка | **Доп.** (Общ). Цель трансформации — привлечь молодых клиентов, поэтому онлайн-трафик будет расти кратно. Точные цифры нужно согласовать с бизнесом |
| S | **Поддерживаемость (Supportability)** | |
| S1 | Новая функциональность депозитов и кредитов в интернет-банке делается силами команды банка в виде отдельных сервисов, без доработки ядра интернет-банка подрядчиком | **АЗТ** (Общ). Первый шаг к микросервисам по паттерну Strangler Fig. В монолите остаются точки входа в UI и маршрутизация |
| S2 | Сервисы независимо разворачиваются через CI/CD. Изменения выкатываются без остановки сервиса (rolling или blue-green) | **Доп.** (Общ). Нужно для 24/7 и 99,9%: плановые релизы не должны создавать простой |
| S3 | Ведётся документация для дальнейшего расширения: API (OpenAPI и AsyncAPI для Kafka), архитектура (C4, ADR), описание процессов и интеграций | (Общ). Прямое требование заказчика |
| S4 | Внешние API версионируются и сохраняют обратную совместимость | **Доп.** (Общ). Сайт, интернет-банк, система КЦ и конвейер выпускаются разными командами и подрядчиками в разное время |
| S5 | Новые продукты и ставки добавляются настройкой каталога, без нового релиза | **Доп.** (Общ). В планах онлайн-продажи большого числа продуктов, релиз под каждый неоправданно дорог |
| S6 | Есть централизованная наблюдаемость: логи, метрики, сквозная трассировка заявки по всем системам, алерты по SLA | **Доп.** (Общ). Без этого нельзя подтвердить 99,9% и быстро найти, на каком шаге «застряла» заявка |
| S7 | Систему КЦ дорабатывают через её механизмы расширения (Java), Кредитный конвейер — через BPMN и обработчики Camunda на Java. Ядра платформ подрядчиков не меняются | (Общ). Исходные данные: обе платформы расширяемы, в банке есть Java-экспертиза. Снижает зависимость от подрядчиков |
| +R | **Ограничения (Restrictions)** | |
| +R1 | Используем технологии, которые уже есть в банке: СУБД MS SQL, Oracle, PostgreSQL; языки .NET (C#), Java (Spring Boot), Python, PHP, JavaScript (React), PL/SQL. Новые технологии допустимы, если они совместимы с текущими платформами и по ним есть экспертиза хотя бы на уровне языка | **АЗТ** (Общ). Ограничивает выбор стека новых сервисов: .NET или Java |
| +R2 | Брокер сообщений — Kafka. Текущая платформа интернет-банка (.NET Framework 4.5) с Kafka несовместима | **АЗТ** (Общ). С Kafka работают только новые сервисы на современном .NET или Java, монолит интернет-банка напрямую к ней не подключается |
| +R3 | В новом процессе интернет-банк не работает с API или БД АБС напрямую | **АЗТ** (Общ). Требование команды АБС и условие доступности 99,9% |
| +R4 | АБС масштабируется только вертикально, её БД уже перегружена | **АЗТ** (Общ). Определяет асинхронную интеграцию и ограничение скорости записи (R3, P3) |
| +R5 | Ядро интернет-банка и его СМС-функционал сопровождает подрядчик, доработок ядра избегаем | **АЗТ** (Общ). См. F6, F16, S1 |
| +R6 | Нового клиента банк не может обслужить без личной идентификации в отделении (115-ФЗ). Сайт принимает только заявки и выдаёт предварительное решение | (Общ). Определяет границу онлайн-сценария для новых клиентов |
